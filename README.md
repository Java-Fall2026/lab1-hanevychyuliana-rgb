# Hotel Booking REST API (Лабораторна робота №7)

Вбудований HTTP-сервер на базі **Jetty 12** та **Jakarta Servlet 6.0**, що відкриває репозиторії готельних кімнат (`RoomRepository`) та гостей (`GuestRepository`) через REST API.

## Таблиця ендпоінтів

### Кімнати (`/api/rooms`)

| Метод | Шлях | Параметри запиту | Коди статусів | Опис |
|---|---|---|---|---|
| `GET` | `/api/rooms` | `type`, `minPrice`, `maxPrice`, `sort` (`number`, `price`, `type`), `order` (`ASC`, `DESC`), `limit`, `offset` | `200`, `400` | Отримання списку кімнат із фільтрацією, сортуванням та пагінацією |
| `GET` | `/api/rooms/stats` | — | `200` | Статистика: загальна кількість, середня ціна, розподіл за типами |
| `GET` | `/api/rooms/{id}` | — | `200`, `404` | Отримання кімнати за її номером (`roomNumber`) |
| `POST` | `/api/rooms` | — | `201`, `400`, `409`, `415` | Створення нової кімнати; повертає заголовок `Location` |
| `PUT` | `/api/rooms/{id}` | — | `200`, `400`, `404`, `415` | Повне оновлення даних наявної кімнати |
| `DELETE` | `/api/rooms/{id}` | — | `204`, `404` | Видалення кімнати за її номером |

## Обробка невідомих полів та параметрів запиту

У проєкті обрано стратегію **суворої валідації (fail-fast)** із поверненням `400 Bad Request`:
1. **Невідомі поля в JSON-тілі:** у спільному `ObjectMapper` (`ObjectMapperFactory`) увімкнено `DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES`. Це захищає API від друкарських помилок клієнта в назвах полів (наприклад, `price` замість `pricePerNight`), які інакше були б мовчки проігноровані.
2. **Невідомі параметри запиту (query parameters):** `RequestHelper.validateAllowedParams` перевіряє всі передані параметри за білим списком дозволених для конкретного ендпоінта і повертає `400 Bad Request` із вказівкою невідомого параметра.

## Потокобезпечність репозиторію

`GenericRepository<T>` синхронізує доступ до внутрішньої `Map<String, T>` за допомогою `ReentrantReadWriteLock` (усі поля репозиторію залишаються приватними). Окремі кроки «перевірити `containsKey`» і «виконати `put`» без блокування небезпечні в багатопотоковому середовищі Jetty, оскільки між перевіркою та записом інший потік може встигнути вставити запис із тим самим ключем (стан гонитви, race condition), що призведе до перезапису замість `409 Conflict`. Використання `writeLock()` робить перевірку наявності ключа та запис (`add`, `addIfAbsent`, `replace`, `removeByIdentity`) єдиною неподільною атомарною операцією, тоді як `readLock()` дозволяє безпечне паралельне читання.
